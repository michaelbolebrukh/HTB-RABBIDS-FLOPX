# Backend product: FLOPX

The product layer is a compute-market terminal's backend: GPU rental prices and
capacity, data-centre infrastructure, compute equities, prediction markets, an
intelligence feed, a forecasting and scenario lab, a research/strategy lab, a
simulated paper-trading desk, a procurement planner and a deterministic query
grammar, served under `/flopx` (architecture: `planning/flopx/architecture.md`).
It replaced the predecessor instance's product layer wholesale on 2026-11-07.

## Shape

`product/flopx/` is the domain package; `product/routers/flopx.py` is the API over
it; `product/flopx/terminal.py` (re-exported as `product.services`) assembles the
request-shaped payloads the routers return. The factory seams are unchanged:
`product.routers.router`, `product.startup.STARTUP_TASKS` (one read-only task,
`check_sample_data`), `product.models`, `product.organisations.SEEDED_ORGANISATIONS`
(empty), `product.payments.CATALOG` (empty), `product.question_flows` (registers
nothing; the import stays so the seam is exercised).

## Provenance is the organising idea

Every record carries a `Provenance` envelope (`product/flopx/provenance.py`): `live`,
`archived`, `sample` or `derived`, with the source, the observation time and a
limitation note. `derived()` records its inputs' kinds and `effective_kind()`
collapses derived-from-sample to `sample`, which is how the UI labels an index
built on sample offers SAMPLE without recomputing anything. `assert_unmixed()`
refuses to aggregate sample rows with observed rows; the FCPI index, the snapshot
medians and the procurement planner all go through it. Every list response adds
`freshness` (generated-at, oldest observation, sources) built from the
provenances actually used, so a payload cannot claim freshness it did not read.

Wire shape is camelCase (the architecture fixes `observedAt`, `generatedAt`);
Python stays snake_case. `schemas.FlopxModel` sets the alias generator once and
accepts both spellings on input, so the sample files (camelCase) validate with the
same models that serialise the API.

## Data tiers

`product/flopx/data/sample/*.json` are AUTHORED datasets, regenerated by
`product/flopx/data/sample_generator.py` (seeded; run it from `fastapi_backend/` as
`.venv/bin/python -m product.flopx.data.sample_generator`). Providers are fictional
on purpose; facilities sit on public data-centre geographies with sample status and
capacity; companies are the eight tickers the brief names with general profile text
and authored reference values; prices sit at plausible late-2026 levels and were
observed nowhere. `data/loader.py` validates every file against the schemas, then
cross-references ids, and holds the result as one shared read-only object per process for
an hour (not through the platform cache, whose memory backend deep-copied it on every read:
about 87 ms a request). A broken
file raises `SampleDataInvalidError` naming the file; the startup task turns that
into a tracked error at boot rather than a 500 on the first request.

Live adapters live in `product/flopx/sources/`, one module per upstream (Vast.ai,
RunPod, Akash, Polymarket Gamma and CLOB, Kalshi, SEC submissions/companyfacts/frames,
Energy-Charts DE-LU and Elexon GB, Hacker News and four investor-relations RSS feeds,
Wikidata data centres, the Yahoo chart endpoint), all keyless, plus EIA API v2 (`eia.py`,
ERCOT and PJM hourly demand, dormant without `EIA_API_KEY`). Whether each may be used
at all is decided by the licence table, `sources/licences.json` (read through
`sources/licences.py`; the frontend holds a byte-identical copy under
`features/flopx/data/`, pinned by tests in both tiers): per source id the terms URL,
the licence string every provenance carries (with "(terms asserted, not verified)"
where the terms were not read in full), the attribution a reader must see, and the
`use`. `off` means the adapter is never called and the source is named nowhere, not
even as unavailable (Vast.ai, whose terms forbid building an index or price comparison
from its data); `display-only` means shown and never archived (Yahoo Finance; the
archive itself refuses any result whose row is not `display-and-archive`); a source id
with no row is treated as `off`. `sources/_http.py` is
the one HTTP seam: a 5 s timeout, a declared User-Agent, `observedAt` from the
upstream's own timestamp or else the response `Date` header with a note saying so,
every time normalised to UTC, the platform cache with a per-source TTL (60 to 900 s;
failures cached for 60 s so a dead upstream is not hammered), a 429/503 that blocks
the whole host for its `Retry-After` (capped at an hour; Yahoo ten minutes when it
gives none; the block lives in the platform cache, so every worker on Redis honours
it), one request a second to the spaced hosts (Yahoo, Wikidata) with the response
awaited under the host lock so a queued caller sees a refusal rather than firing, and
a `TRANSPORT` seam the tests replace with an httpx `MockTransport`.

**Reads never wait on an upstream (B-PERF, 2026-11-08).** `product/flopx/refresher.py` is
started by the product startup task in every gunicorn worker (one per process; refused
under pytest). It switches `_http` into serving mode: a request thread is answered from
the newest answer the process holds, keeping the time the source gave it, or before the
first answer with `warming`, which the read reports in `freshness.unavailable` while
it falls back to the sample tier; an answer older than twelve times its TTL is not
served. Every request shape is a job; the refresher's own thread fetches each when it
reaches 80% of its TTL (a failure waits its failure TTL or the host's `Retry-After`),
at most four at a time, with the per-host spacing above, and drops a non-seed job
nobody has asked for in 30 minutes. The terminal's user-independent reads go through
`refresher.composed`: the newest composition of the same arguments is returned at once
(shared, not copied) and recomposed in the background with the refresher's own session
after an upstream answer changes or after 120 s, at most one sweep a minute, the
inferred-state inputs built once per sweep. The evaluation reads are recomposed on age
alone (ten minutes), since no live answer can change a score over past closes. Each
composition carries its own `generatedAt`. With the refresher stopped, every read
composes exactly as before, which is how the suite exercises it. Known limit: the very
first read of a key after a restart composes inline (CPU and the archive, never an
upstream); for `/flopx/research/evaluation` that is the evaluation harness itself,
about 1.5 s on one local core. Memory of a served worker (B-MEM, 2026-11-08): the
process holds every upstream answer, so an adapter whose body is large passes
`fetch_json(..., reduce=)` to hold only the slice it reads (SEC companyfacts: the
five concepts' tags, 40 MB of parsed JSON to under 1 MB for six filers);
`archive.extend` reads only rows past the series' last point; an archive read shares the
repeated provenance strings (licence, note, source, URL) across its rows instead of
holding one copy per row; and the refresher hands
glibc's freed heap back to the OS after warm-up and after each sweep that did work
(`release_freed_memory`), because a sweep's transient rows otherwise stay resident
and the one-worker instance ratchets towards its 512 MiB cap. The sweep itself reads the
archive as column tuples, never ORM rows (B-MEM2): the power series are aggregated in SQL
to hourly means up to 90 days and daily means beyond, each point noting how many slots it
averages, and the evaluation's equity closes are read once per sweep; a sweep's traced
peak fell from 90 MB to about 20 MB on the two-year archive. Observation times
are the value's, never a bar start or a future slot: a Yahoo daily bar is stamped at
the session close (or its last trade while the session runs), and a day-ahead power
price is kept only once its delivery slot has started, so every "current" read of a
power series agrees. An adapter returns a `SourceResult`: `available` with records
and a `live` provenance, or `unavailable(source, reason)`; it logs at warning and
never raises into a router. `sources/_mapping.py` maps upstream GPU names onto the
six models by exact variant only (an H100 PCIe is dropped, never relabelled an SXM),
and upstream geographies onto region ids, falling back to a lower-case country code
the adjustment treats as factor 1.0. The Alpaca adapter stays dormant unless all
three `PRODUCT_ALPACA_*` settings are present.

`terminal.py` merges live over sample with two rules a reader can rely on: a list
(offers, markets, feed, facilities) holds live and sample rows together, each row
carrying its own provenance; an aggregate (an index, a heatmap cell, a median) is
computed over one provenance class only and labelled with it, so a model with live
asks gets a live-only index and a model without keeps its sample one. Every response's
`freshness` names each source used with its newest observation (`sourceDetails`) and
each source that did not answer with the reason (`unavailable`). Independent adapter
calls fan out on a small thread pool, so a cold overview costs the slowest upstream,
not the sum. Live change detection compares live offers with the archive's last
observation and reports price moves, availability flips and appearances; it cannot
report a live offer that disappeared, because the archive holds numbers, not offer
descriptors.

`archive.py` appends every successful live observation to `flopx_observations` in the
request session, inside its own try/except so an archive failure never fails a read.
Series ids embed source and entity (`offer:<provider-offer>:price`,
`index:fcpi:<model>`, `market:<venue id>:yes`, `equity:<T>:close`,
`energy:<zone>:<measure>`, `fundamental:<T>:<concept>`), so the table's unique
(series_id, t) is the idempotency key; an unchanged value is re-archived at most
hourly, every move is kept. `archived_series` lets series, X-Ray and forecast extend a
sample series with newer archived points, each labelled `archived`; `series.resolve_series`
still never blends two classes into one point.

The licence table governs reads as well as writes. Nothing is deleted, but `archive.refusal`
withholds a row whose source is now `off` or display-only (the Vast.ai asks stored before
Vast was switched off), a row dated after its own fetch or after now (day-ahead slots
archived before their delivery time), and an FCPI point that does not record its basket
(the sources behind the median) or whose basket holds a source that is now off. Every
archive read, `series.archived_series` included, goes through it, and `record` refuses the
same rows on write. Index points are written with their basket; `terminal._index_for`
marks a basket change between consecutive points as a series break (`breaks` on the index
and the series payload, `historyBreak` on a forecast), and change, momentum, forecast,
scenario and the inferred engines read only the points from the last break on.

**The research archive (decision G13) and the fundamentals merge policy.** Two of the
founder's WRDS extracts live in the same table under the licence use `research-archive`
(`sources/licences.json`, rows `wrds-crsp` and `wrds-compustat`): the CRSP daily closes
(`equity:<T>:close`, loaded by `tools/wrds_load.py`) and the Compustat quarterly fundamentals
(`fundamental:<T>:revenue_q`, `fundamental:<T>:capex_q`, `fundamental:<T>:total_assets`,
loaded by `tools/compustat_load.py`). Neither file is ever committed: the deployment mounts
them as the secret files `/etc/secrets/flopx-crsp.csv` and `/etc/secrets/flopx-compustat.csv`
and the startup task `load_research_archive` upserts whichever is present, idempotently, with
one log line each. Compustat values are stored in USD (the extract is in millions) at the
fiscal period end, with the report date as the point's `observed_at` and in its note, so a
point-in-time reader can tell when the figure was knowable; the quarter's own capex is derived
from the fiscal year-to-date figure (quarter 1 is the year-to-date itself, a later quarter is
the difference from the previous quarter of the same fiscal year, and a quarter with no
derivable predecessor gets no point). Both loaders' `delete` modes remove exactly their own
rows when the project comes down.

**Power-price history from the internet (N-DATA, 2026-11-08).** The live energy adapters ask
for yesterday and today only, so `tools/history_backfill.py` fills the archive with the last
two years of the two openly licensed day-ahead series: Energy-Charts DE-LU
(`energy:DE-LU:day-ahead`, CC BY 4.0, one request per 60 days; 15-minute slots since
October 2025, hourly before) and Elexon BMRS GB (`energy:GB:market-index`, the BMRS open
data licence, at most seven days per request, so about 105 calls). Each slot is parsed by the
live adapter's own parser, stored with provenance `archived`, the source id, the licence line
and a note naming the slot, the attribution and the backfill, with the request window beside
it as an audit trail; writes go through `archive.upsert`, so a rerun writes nothing. The run
is resumable (it reads which UTC days the archive already holds and fetches only the gaps) and
bounded (150 requests or 15 minutes per run, the rest on the next run). The startup task
`start_history_backfill` runs it on a daemon thread 30 s after boot under the cross-worker
advisory lock `flopx-history-backfill`; the CLI is `python -m product.flopx.tools.history_backfill
run|status`. The reads pick it up without a live answer: the inferred-state inputs read every
licensed live-only power series from the archive (the last 120 days, once per sweep: the whole
two-year DE-LU series measured 2.2 s to read on one local core against 0.17 s for 70 days, which
a 0.5-CPU instance cannot pay every minute), so the pressure engine's power-stress median and
the infra energy change have their 30 days when the upstream is warming or blocked (measured on
the real two-year payload: eu-de power-stress raw 0.50, latest 289.64 against a 30-day median of
193.55 EUR/MWh), the overview's two energy indicators fall back to the newest archived slots
labelled archived, and the series read takes the archive for the requested range only, up to
the full two years. The evaluation harness's energy feature consequently has data only for
origins inside that 120-day window. The same row of `licences.json` governs the history as the
live slots.
Known blind spot: a day the upstream answered partially counts as held and is not re-asked.
Not loaded, and why: ERCOT and PJM day-ahead PRICE history (PJM Data Miner, gridstatus and
ERCOT's public API all need a registered key, and EIA's API carries no wholesale price at all, see
N-EIA below), so `energy:ERCOT:day-ahead` stays the authored sample and `us-tx`/`us-va` have no
real power-stress input. No region maps to the GB zone, so the GB history reaches the overview
and the series read, not a pressure cell.

**ERCOT and PJM hourly demand from the EIA API, behind one key (N-EIA, 2026-11-08).** The brief
asked for the two zones' day-ahead wholesale price from EIA API v2, falling back to the real-time
LMP. Neither exists there: every route under `/v2/electricity/` was listed on 2026-11-08, the `rto`
routes are Form EIA-930 (demand, day-ahead demand forecast, net generation, interchange, in MWh,
hourly and daily, per balancing authority) and the only price in the tree is the monthly retail
average by state; EIA's wholesale day-ahead prices (ERCOT North, PJM West) are an ICE spreadsheet
republished with permission under third-party copyright, outside the API and the public domain,
and are not read. So `sources/eia.py` takes the load side the key does unlock:
`energy:ERCOT:demand`, `energy:ERCOT:demand-forecast`, `energy:PJM:demand` and
`energy:PJM:demand-forecast` from `electricity/rto/region-data` (respondents `ERCO` and `PJM`,
types `D` and `DF`, hourly UTC periods, the hour's start as the observation time, slots not yet
started left out as Energy-Charts' future slots are), licence row `eia`, "US public domain (EIA)",
`display-and-archive`. They are never written under an `energy:<zone>:day-ahead` id and the
power-stress factor and infra energy read do not consume them: the US zones' price input is
unchanged until a licensed price source exists. Without `EIA_API_KEY` (settings) the adapter is
dormant and invisible: `terminal._energy_calls()` and `terminal.live_series()` leave the four ids
out, so no job registers, no `not-configured` entry reaches a freshness block and the series ids
are unknown, exactly as before. With it, the two zone calls join the energy call list (and so the
refresher's boot seed, which is built from that list), the four ids answer through the series
read with the archive merged in, the live slots are archived each sweep, and the history backfill
gains four `HistorySource` rows (one type per request, 200-day chunks of 4800 rows against the
API's 5000-row cap, so two years is four requests per series), skipped with a log line while the
key is absent. The key travels only as the `api_key` query parameter; `_http` logs host and path
only, the cache key is zone and window, no `Fetched.url` is copied anywhere, and `api.eia.gov` is
spaced at one request per second per process (the API reports an `x-ratelimit-limit` of 10 on the
demo key, window unstated). Recorded fixtures under `tests/fixtures/recorded/eia/` (key redacted
from the recorded URL) drive `tests/test_eia_grid.py`; the live key was never present in a test run.

**A year of GPU rental price history from GetDeploying (N-GPU, 2026-11-08).** FCPI's own
archive began on 2026-11-07, so the one lawful GPU price history found (N-DATA) is loaded beside
it as its own labelled series, never into it. `sources/getdeploying.py` reads the weekly CSV at
https://getdeploying.com/dataset/gpu-prices (CC BY 4.0, read from the dataset page: "Credit
GetDeploying and link to the license"; the licence covers the dataset files only, not the site or
its API; 103 GPU models, 94 providers, 53 trailing weeks, the median, minimum and maximum of each
week's daily captures of advertised asks per model and billing type; the CSV is 1.1 MB where the
JSON is 4.1 MB, within 77 KB of `_http`'s 4 MiB body cap). The adapter keeps the `ON_DEMAND` rows of
six family slugs and maps them to FLOPX ids (`nvidia-h100` to `h100-sxm-80gb`, `nvidia-h200` to
`h200-sxm-141gb`, `nvidia-b200` to `b200-sxm-192gb`, `nvidia-a100` to `a100-sxm-80gb`, `nvidia-l40s`
to `l40s-48gb`, `nvidia-rtx-4090` to `rtx-4090-24gb`); a GetDeploying family pools boards (H100 SXM
and PCIe, A100 40 GB and 80 GB), which the note on every point says, and the other 97 slugs are
ignored by rule, since a model FLOPX does not index has no series to sit beside.
`tools/getdeploying_load.py` stores three points per model and week, `gpu:<model>:getdeploying:
weekly-median`, `:weekly-min` and `:weekly-max`, unit USD/GPU-hour, provenance `archived`, source
`getdeploying`, the licence line, and a note carrying the CC BY 4.0 attribution with the licence
link, the week, the slug and the provider and offering counts (the same fields beside the
provenance as an audit trail). A week's observation time is its END, the Monday 00:00 UTC after the
dataset's Monday `date`: the dataset says the newest week changes until its Sunday is captured, so
the running week is reported as pending and lands on the first load after it ends. Writes go through
`archive.upsert`, so a reload writes nothing and a revised week is rewritten; one request per load.
The startup task `load_research_archive` runs one load at boot (refusing under pytest, since the
source is keyless) and the refresher's hook `refresh_if_due` runs one per ISO week across workers (a
platform-cache marker, a failed week retried after 600 s), so the just-finished week lands on the
first tick of the new week; the CLI is `python -m product.flopx.tools.getdeploying_load
load|status|delete`. The series read (`/flopx/gpu/series?id=gpu:h100-sxm-80gb:getdeploying:weekly-median`)
serves them to every reader, archived, with the licence line in `freshness`. Deliberately NOT
done: nothing is written under `index:fcpi:*` or `gpu:<model>:on-demand:*` (a third-party weekly
median of advertised list prices is not an FCPI point). The series is a history reference beside
FCPI; the one engine that reads it is the pressure momentum factor, under the labelled fallback
rule in the next paragraph (N-GDH-BE), which the founder chose over leaving momentum empty.
Also not done here: the research lab's series catalogue is built in the frontend from the sample
series (`next-pwa/product/features/flopx/features/research/series-lab.tsx`, `SERIES_OPTIONS`), so
listing these ids there is a frontend change; the backend offers no catalogue endpoint.
Known blind spots: GetDeploying's figures are advertised prices converted to USD at the ECB rate,
not checked as rentable, and the pooling of boards under a family slug means a week's median is
not a like-for-like comparable of the FLOPX model's own on-demand asks.

**Momentum may read GetDeploying while FLOPX's own index is too short (N-GDH-BE, 2026-11-08).**
`pressure.momentum_series_for` picks one series for the 30-day price-momentum factor and never merges
two: a regional on-demand series when one exists (unchanged; GetDeploying is global); else the
model's FLOPX index (`index:fcpi:<model>`) when the points known at the cell's date reach back the
full 30 days; else, when the archive holds `gpu:<model>:getdeploying:weekly-median` with points
spanning those 30 days, that series, with the factor's `scope` set to `getdeploying-weekly`; else the
short index as it stands (momentum empty, "fewer than 30 days" as before); else the global sample
series. The choice is made from the points known at the cell's `as_of`, so a history recomputed at a
past date decides as that day would have. On the fallback the factor's note reads "30-day change of
GetDeploying's weekly median (CC BY 4.0), FLOPX index history too short (N days)", N being the distinct
days of FCPI history known at the date (0 when the model has no index yet), followed by the two week
ends read and their gap (weekly points sit 35 days apart across a 30-day window); its evidence is the
two GetDeploying points' own provenance (kind archived, source getdeploying, licence CC BY 4.0), so the
cell's `inputKinds` and `sampleShare` say what was read. `terminal.InferredInputs` reads the whole
weekly-median series for every model from the archive under its own id (`GETDEPLOYING_HISTORY_DAYS`,
400 days), so the pressure grid, the infra scenario's cell and the evaluation feature all see it;
nothing is read without a database, so the sample path and the engine fixtures are untouched (the
fixtures carry no GetDeploying series). Consequence on the recorded fixtures: with the loader's 52
weeks in the archive and only sample asks, every cell of all six models gets a GetDeploying momentum
(the sample index is not FLOPX history, so real archived weeks outrank it), and a model whose live
index began on 2026-11-07 gets one too until its own index spans 30 days, at which point the index
takes over by rule. The infra scenario's price path (`scenario.project_infra`) keeps the pre-N-GDH-BE
chain via `weekly_fallback=False`, because it steps by the day from the series it is handed and a
weekly series would mis-scale its drift. Blind spot: the TypeScript engine port (`engine/pressure.ts`)
carries its own `momentumSeriesFor`; the frontend half of N-GDH-BE mirrors this rule there, and no
engine fixture case pins the fallback yet.

The merge rule for fundamentals is `fundamentals.py`'s and `terminal.company` /
`terminal.companies` apply it: live SEC EDGAR facts remain the latest-filed values wherever
SEC answered for a period; Compustat supplies the history and the latest quarter where SEC has
nothing; "the same period" is the concept, the period's length class (quarter, annual, instant,
read off the `period <start> to <end>` clause both sources write in the note) and the month the
period ends in, so a 10-K's twelve-month revenue never replaces or is compared with a quarter.
Every row keeps its own provenance, and `fundamentalsSummary.latest` names the source behind
the newest value per concept. The derived figures (`revenueGrowthYoY`: the latest quarter
against the quarter ending about a year earlier; `capexIntensity`: the latest quarter's capex
over its revenue; both `derived`, with `sources` and `inputKinds`) are public on
`/companies` and `/companies/{t}` for every reader. The raw Compustat rows follow the
`research-archive` gate exactly like CRSP: a signed-in account's `fundamentals` list is the
merged observed rows; an anonymous reader's is the SEC rows or the authored sample, as before,
and `/gpu/series?id=fundamental:<T>:revenue_q` answers 404 anonymously. The authored sample
fundamentals carry no period clause and so never produce a derived figure.

Tests never reach the network: the router test fixtures install a 503 `MockTransport`
on `_http.TRANSPORT`, the adapter tests replay the trimmed real responses under
`product/flopx/tests/fixtures/recorded/<source>/`, and `test_flopx_merge_policy.py`
pins the two merge rules. `product/flopx/tests/fixtures/engine/*.json` are the engine
drift fixtures (inputs and expected outputs produced by the Python engines;
`export.py --check` fails if they would change) that the frontend's TypeScript port is
tested against.

## Analytics, and what each refuses

- **Index** (`indices.py`): FCPI = median of comparable asks per GPU model, with
  coverage, normalisation list and limitations in every payload; history is the
  model's on-demand series rescaled to today's adjusted median (stated as a
  limitation). Mixed tiers raise `MixedProvenanceError`.
- **Adjustment** (`adjust.py`): quoted to comparable price as named multiplicative
  steps (interruptible and reserved discounts reversed, region normalised to the US
  baseline, memory variant by a square root). The assumptions are constants reported
  back in `reference`.
- **Change detection** (`changes.py`): price moves over 2%, availability flips, new
  and removed offers between two snapshots, each with before/after and evidence links.
- **Forecast** (`forecast.py`): naive, drift, seasonal-naive, SES; intervals from
  in-sample one-step residuals widened by the FPP3 factors; rolling-origin backtest
  with MAE/MAPE and MAE relative to naive; `chosen` is naive unless a baseline beat it
  by 2% out of sample. Refuses when history < 2 x horizon
  (`InsufficientHistoryError` with the numbers) and drops seasonal-naive with a reason
  under two seasons.
- **Scenario** (`scenario.py`): authored elasticities over named assumptions on the
  drift baseline, linear ramp, labelled `demonstrative`; unknown assumptions are
  reported as ignored, never silently dropped.
- **X-Ray** (`xray.py`): inner-join alignment on date, normalised to 100, Pearson on
  log returns at lags -5..+5 with n, feed events annotated by matching entities,
  caveat tokens (`association-not-causation`, `sample-data`, `short-window`).
- **Procurement** (`procurement.py`): ranks offers that can run a workload by
  expected cost per unit of performance, with low/high ranges, spot restart overhead,
  deadline and budget checks, and trade-off tokens the UI maps to copy.
- **Query grammar** (`ask.py`): entities (tickers, GPU aliases, regions, providers),
  measures, periods, actions and workload quantities; returns intent, route with URL
  filters, an explanation listing matched and unmatched tokens, and actions (orders
  and closes `requiresConfirmation`). No LLM; the platform AI service may upgrade it
  when a key exists, the grammar stays the fallback.

## The inferred-state layer (architecture §10)

The refinement adds a layer that reconstructs hidden state from the observations
above and says, on every element, which of the four classes it is: `observation`
(a sourced fact), `inference` (a hidden state reconstructed from observations, with
`method`, `inputKinds` and `uncertainty`), `forecast` (horizon, interval, and
`exploratory: true` where no reliability has been measured) or `decision`
(`status`, `rationale`, `risk`). The `statementClass` field is on every new payload;
nothing in this layer is ever labelled measured, calibrated or validated unless a
test computed it from data.

- **Pressure** (`pressure.py`): the Compute Pressure Index `cpx-v1`, per (region,
  GPU model) cell, 0 to 100, banded slack / balanced / tight / acute (50 exactly is
  balanced). Six factors with stated weights, each normalised to [-1, 1] with its
  evidence provenances; a factor with no data is listed with `normalised: null` and
  the remaining weights renormalise. `contradictions` lists the factors arguing
  against the score's side of 50; `uncertainty.label` is `exploratory` (coverage
  under 3 asks, fewer than 4 factors, or more than half the inputs sample) or
  `indicative`, never `measured`. History is honest about its thinness: the two
  sample snapshots, then one point per archive day of live asks, and `historyBasis`
  says so. On the sample data no cell is acute (the highest is us-va H100 at 62.6,
  tight) and every cell is exploratory because every input is sample. Each cell
  also carries `rental`, the X-Ray's rental economics (N-XRAY): with regional asks,
  the cell's comparable median and premium over the model's global median (the
  price-premium factor's own numbers, `basis: regional-asks`); without them,
  `basis: global-fallback` with the model's global median of the asks the cell was
  scored from and GetDeploying's archived weekly median (latest week known at the
  cell's date), `premiumPct: null` and `premiumLabel` "n/a (no regional asks)", so
  the tab is never empty; `basis: none` only when neither exists. The fallback is
  a reading for the tab, never an input to the factor, which stays "no data".
- **Effective supply** (`effective_supply.py`): operating x utilisation (an
  assumption, 0.70 in a stated 0.5 to 0.9 range) plus under-construction MW x a
  completion probability from months late; announced and planned MW are listed and
  never counted, `reported` records are listed and counted nowhere. GPU equivalents
  appear only when every counted facility carries an estimate.
- **Exposure** (`exposure.py`): companies reached by a region, with `documented`
  true only for a facility owner or operator record or an SEC-sourced filing
  mention; the authored profile tags give `documented: false`. Sensitivity is the
  authored equity elasticity from `scenario.py`, stated as an estimate. Every row
  says in words what it rests on (N-XRAY): `role` is the profile role the
  sensitivity is read off, `tieKind` is `documented` or `authored`, `tieBasis`
  names the record, filing or profile tag, and an authored row carries `tieNote`
  "authored tie from company profile, not a filing" (also the row's provenance
  note). Documented rows sort first; a covered region never answers with an
  empty list, because the profile tags reach every region, and never passes an
  authored sample facility off as a document. `/flopx/exposure` takes the optional
  user and overlays the signed-in account's paper position per row (`position`:
  quantity, side, average cost, value at the sample close, weight) on top of the
  shared user-independent composition, which it never mutates; anonymous readers
  and accounts with no desk get `position: null`, and a read creates no account.
- **Anomalies** (`anomalies.py`): five deterministic rules (bottleneck,
  announcement mismatch, price dispersion, overhang, divergence) over the pressure
  grid with stable ids `anomaly:<type>:<region>:<gpu>`; severity is 1 plus the band
  distance plus one when no factor contradicts, capped at 5, with the basis text in
  the payload. Cells with no asks are skipped. A factor the rule rests on is listed
  as supporting only, never also as contradicting. Divergence compares the index
  with the documented companies' basket when any link is documented; otherwise
  (decision G11-b) with the companies on authored sample facility records in the
  region, else the authored profile links, and then says so in the headline ("the
  basket linked by authored sample facility records ..., not a filing"), sets
  `measures.basketBasis: authored` and adds the links' sample provenance to its
  inputs. The sample data fires eight (one announcement mismatch, seven authored-basket
  divergences), all severity 1. An anomaly signal's `no-documented-exposure` note names
  the basis the listed links rest on.
- **Infrastructure scenarios** (`scenario.project_infra`): recompute supply and
  pressure under `delay-facility` (a delay is lateness), `complete-facility` (counts
  at stated capacity inside the horizon), `energy-shock`, `demand-shock` and
  `utilisation`, then project the comparable price with the elasticity
  `pressureDelta / 50 x 0.25` on top of the drift baseline, widened by the
  assumption uncertainty, and trace the move into exposed companies. The response
  is `statementClass: forecast, conditional: true` and returns the baseline and the
  conditional path side by side. The supply-to-pressure link (50 points per 100%
  supply change) is an authored assumption the payload names. The projected series
  is a GPU price, so every path value is floored at zero and the caveat
  `price-band-floored-at-zero` says when the widening drift band was cut there.
- **Evaluation** (`evaluation.py`): walk-forward, point in time, over daily closes
  at 1, 5, 21 and 63 days; `baseline` (trailing drift), `augmented` (ridge on three
  compute features, fitted on the trailing origins whose outcomes were known) and
  `combined` (plus a feed-event feature), with MAE, RMSE, sign hit rate, 80% band
  coverage, skill against the baseline and a verdict that admits `inconclusive` and
  `insufficient-sample` (never omitted). Skill is like for like: the baseline RMSE
  is taken over exactly the origins the model scored (`baselineRmseMatched`). A
  feature that is missing or constant over the window is dropped, and one constant
  over an origin's training window is left out of that fit, so no forecast is ever
  the intercept alone: a ticker with no varying compute feature reports
  `insufficient-sample` ("no compute feature available"), and `combined` forecasts
  only where the event feature varies. When the FCPI index has no history covering
  the window, the raw on-demand series stands in and the feature is named
  `gpu-price-change-30d`; `select_price_feature` makes that choice and both tiers
  call it. Ridge is plain Python. The /research verdict sentence is built from the
  payload; on sample closes the page says this tests the method on authored data.
  `_evaluate_ticker_uncached` is mirrored by the route-handler composition and pinned
  by the `evaluation_terminal` drift fixture: the sample dates always read the sample
  offer snapshots, and the pressure, price and power features read the sample bag's series,
  facilities and markets plus only what was observed by the last scored close (never the
  live FCPI index, whose route-handler history would be look-ahead), so both tiers give one
  verdict per (ticker, horizon); an archived input that did reach a scored close would be
  named in `inputKinds`. On top of the per-ticker scores the view adds three research blocks
  computed across the tickers it evaluated, each with provenance `research` and none of them
  touching a verdict: `crossSection`, per (horizon, model), the mean Spearman IC across tickers
  per origin date (dates with fewer than three tickers are not scored; the payload carries the
  number of dates, the mean, its t-statistic and the share of dates with five or more tickers,
  and the note says the t-statistic is optimistic because origins overlap for h > 1);
  `tradable`, per (horizon, model), the Sharpe of the simplest use of the forecast (long when
  positive, short when negative, held h trading days from non-overlapping origins, each trade
  less the ticker's own mean realised return over its traded origins so riding the drift scores
  zero, pooled across tickers, annualised by sqrt(252/h); no costs, no slippage, a research
  number); and `historyCoverage`, per ticker, the first and last close, trading days, span in
  years and origins scored per horizon, so "enough history?" is answered with numbers. The
  per-ticker composition hands the view every scored forecast with its exit date (the `panel`,
  cached beside the evaluation under `flopx:evaluation:v5`) rather than the 60 rows the
  evaluation itself shows, which is why the per-ticker payload and the engine fixtures are
  unchanged by these metrics. The
  portfolio evaluation reruns each strategy with 5 bps per fill, a price-only twin
  (the compute feature replaced by the asset's own momentum), each row's own
  instrument buy-and-hold (`benchmarkTicker`) and an equal-weight benchmark of the
  eight; the hit rate comes with `roundTrips`, its denominator. A strategy's own page
  shows the same costed compute run (one backtest per strategy and variant, never a
  second uncosted one). Results are cached as
  plain data for ten minutes per ticker.
- **Signals and the decision ledger** (`signals.py`, `strategies.py`,
  `flopx_strategy_decisions.status`): a strategy step now PROPOSES (status
  `proposed`, no order); `POST .../decisions/{id}/accept` is the only path that
  submits, and the row reads `submitted`, then `filled` or `rejected` from what the
  broker did, or `skipped` with `risk-limit` / `strategy-not-followed`. A proposal is
  only the rule's latest view: the next forward step for the same strategy marks earlier
  forward proposals `skipped: superseded` (a replay supersedes only earlier replays; the two
  never supersede each other), and past `t + horizon` a proposal is `skipped:
  expired` (swept before every step, accept, strategy read and fund read), so a stale proposal is
  never executed at today's price as if current; accepting either is refused (422,
  `decision-superseded` / `decision-expired`). Accept claims the row atomically
  (proposed to submitted in one conditional UPDATE) before placing, so of two racing
  accepts one places and the other gets 409; a broker failure after the claim hands the
  proposal back. A step can REPLAY the rule at a past sample date (`asOf`), recorded with
  `rationale.replayOf` (served as `replay_of`) so it never reads as today's output. A replay
  is hindsight, never forward evidence: its fills carry origin `replay:<strategy>` and are
  attributed to that group (keyed from the decision, so older fills count right too), the
  strategy's forward `orders` and `proposed` counts exclude replays (`replays` counts them),
  replaying a date that already has an open, filled or lapsed replay returns that decision
  instead of piling another onto the signal, and a replay of a date whose horizon has passed
  is recorded `skipped: expired`, never proposed. Hold rationales say
  `already-held` / `nothing-held` when a threshold fired on a held or empty position (the
  event rule too, when the qualifying item names only held tickers), and a forward hold is
  skipped with that reason; `within-band` only between the thresholds. Each buy or
  sell names its signal (`signal:<strategy>:<ticker>:<date>`); the anomaly detector
  yields one signal per anomaly, skipped with `no-documented-exposure`,
  `insufficient-sample` or `strategy-not-followed` (no strategy consumes anomaly
  signals today). A signal's chain is signal, baseline forecast at its date,
  decisions, orders and, once the horizon has passed, the realised outcome from
  closes observed later. Signals are reconstructed from the ledger and the current
  anomalies, never stored, so they cannot contradict their decisions. Migration
  `20261107_02` adds the ledger columns, add-only and reversible.
- **Fund** (`fund.py`): the signed-in account's holdings with exposure by cluster
  (`data/sample/clusters.json`, an authored editorial grouping), an equity curve
  rebuilt from fills and daily closes (a `derived` series with its inputs' kinds and
  its newest input's observation time, no snapshot table), drawdowns, turnover, an
  equal-weight benchmark from the first fill, attribution, and target positions from
  the latest proposals, kept apart from holdings. `drawdowns()` is the ONE drawdown
  computation, shared with the desk's account read: the running peak starts at the
  starting cash (first-fill slippage counts) and the current mark is the path's last
  point. Attribution is realised plus unrealised P&L by FIFO lots, each lot keeping the
  origin (or signal kind) of the order that opened it, so a closed round trip has no
  open value and a strategy lot closed by hand counts to the strategy. The account
  value carries `accountProvenance` (its marks' kinds, SAMPLE when a mark is sample);
  each target position carries provenance, `expiresAt` and a stated risk: one standard
  deviation of its value over the horizon from the closes known at the decision.
- **Infra reads** (`infra.py`): energy per zone (only ERCOT has a sample series; the
  other seven zones are listed as missing), projects with their stage exactly as the
  record says, and the grid with a constraint flag that is the power-stress factor
  at or above 0.5.
- **The composed brief** (`assistant.py`, `ask.py` intent `brief`): "what is
  happening in <region|ticker|gpu>" returns sentences built from the product's own
  evidence, each with its evidence ids and statement class, `method:
  composed-from-evidence-v1`, `notLanguageModel: true`. A language-model drafting
  mode is a documented stub behind `ANTHROPIC_API_KEY` that returns the composed
  form unchanged; no key is set anywhere.

`terminal.InferredInputs` is the one place these engines meet the live-over-sample
merge rule: per GPU model the asks are live rows when any exist, else sample rows;
series are the sample series extended by the archive plus the live index where a
model has live asks; facilities, markets and feed are the merged lists. Routes:
`/pressure`, `/pressure/{region}/{gpu}`, `/supply`, `/anomalies`, `/anomalies/{id}`,
`/scenario/infra`, `/exposure`, `/research/evaluation`, `/research/evaluation/portfolio`,
`/research/signals`, `/research/signals/{id}`,
`/research/strategies/{id}/decisions/{decisionId}/accept` (signed in), `/fund/summary`
(signed in), `/infra/energy`, `/infra/projects`, `/infra/grid`. Drift fixtures for
every engine here sit beside the older eight under `tests/fixtures/engine/`
(`pressure`, `effective_supply`, `exposure`, `anomalies`, `infra_scenario`,
`evaluation`, `signals`, `assistant`).

## Paper desk and strategies

`paper/broker.py` is the whole simulated broker: one account per user (1,000,000 USD,
buying power = cash, no margin, no shorting), market and limit orders by quantity or
notional, fills at the last close plus 5 bps against the trader, commission 0,
rejections persisted with reason tokens (`insufficient-cash`, `insufficient-position`,
`unknown-instrument`, `market-data-unavailable`), close-one and close-all (refused
without `confirm: true`), positions with average cost, realised and unrealised P&L,
exposure by compute-exposure tag, and a drawdown figure against a persisted equity peak
(the account READ the desk serves overrides it with the fund's drawdown computation, so
the two screens show one number).
Money is Decimal in integer cents. The price lookup is injected: the routers wire
Yahoo-then-sample (`terminal.price_lookup_for`) and every fill records the provenance
of the price it used, so a fill on a sample close says so. `origin` is `manual` or
`strategy:<id>`. No real brokerage path exists.

`strategies.py` holds three transparent rules (`divergence`, `supply-regime`,
`event-reaction`) over data the model already has. `decide()` sees only data known at
the decision time (series cut at t, feed items observed by t) and records the values
it used and the signal it acted on. Backtests run over the sample window, long/flat,
labelled `backtest` with derived-from-sample provenance, optionally with costs per fill
and in a price-only variant; `POST /flopx/research/strategies/{id}/step` (signed-in
user) records a `forward` decision for that user's account with status `proposed` and
places nothing; the accept route is what submits (see the inferred-state layer). No
realised profit is claimed beyond the simulated ledger. `sources/alpaca.py` is imported
by no router, pinned by `test_flopx_no_brokerage.py` in a clean interpreter.
