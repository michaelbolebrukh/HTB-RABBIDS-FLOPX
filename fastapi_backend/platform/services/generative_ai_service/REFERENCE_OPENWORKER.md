## 1. TurnEngine loop (`coworker/engine.py`, 1199 lines)

**Shape.** Not a state machine with named states — one `async def _loop()` generator yielding typed `Event`s (`events.py`: TURN_START, ASSISTANT_DELTA, REASONING_DELTA, ASSISTANT_MESSAGE, TOOL_PROPOSED, PERMISSION_REQUIRED, TOOL_STARTED, TOOL_FINISHED, ITERATION_END, COMPACTING/COMPACTED, PLAN_PROPOSED, DIRECTORY_REQUESTED, INTERRUPTED, ERROR, TURN_END). Per iteration (max 12): compaction checkpoint → stream model (blocking provider bridged via thread+queue, raced against a cancel event so a stalled pre-first-token stream can't wedge the turn) → append assistant message → if no tool calls, end (after draining queued "steering" messages) → else `_handle_tool_calls` → repeat. Canonical history is `self.messages` in OpenAI shape with display-only sidecars (`ts`, `source`, `_display`, `reasoning`, `usage`, and whole `role:"notice"` messages) stripped by `_outbound_messages()` — the sole provider feed.

**Tool dispatch.** Authorize ALL calls of one assistant turn first, sequentially (approvals are interactive), then execute: metadata-declared `risk_level=="low" && !requires_approval` calls run concurrently via `asyncio.gather(to_thread(...))`; everything else strictly serial in call order. Tool exceptions never propagate: `_execute_sync` returns `({"error", "error_type"}, "error")` as an ordinary tool result. Unknown tool → tool-error message, loop continues.

**The no-orphan invariant** is the loop's strongest discipline: *every* `tool_call` id in history gets a `role:"tool"` answer — denied (`_tool_error_message` with reason), interrupted ("interrupted by user"), or a real result — because hosted chat templates reject orphaned tool_calls and durable-resume enumerates unanswered ones. Interrupt (`request_interrupt`) works from any state: mid-stream (producer thread drops between chunks; the partial the user watched arrive is persisted as an assistant message), mid-tool (injected `interrupt_hooks`, e.g. the shell executor's kill), mid-await on an approval (`_interruptible` races every human-await against the cancel event, resolving as DENY/interrupted), or between iterations.

**"Needs human" = an awaited callback, not a state.** `PermissionEngine.evaluate` returns `Decision(allowed, reason, needs_user, rule)`; on `needs_user` the engine emits PERMISSION_REQUIRED and `await`s an injected `approver(PermissionRequest) -> ApprovalOutcome{ONCE, ALWAYS_TOOL, ALWAYS_COMMAND, DENY}`. Three more interactive tools (`ask_user`, `propose_plan`, `request_directory`) bypass the permission path entirely — the human's out-of-band answer IS the consent — each via its own injected async callback. Suspension is durable because `PermissionRequest.tool_call_id` rides into the Inbox item: `resume()` (post-restart) finds the trailing assistant message's unanswered tool_calls, re-runs `_handle_tool_calls` on exactly those, and the callbacks find the already-resolved Inbox item (idempotent by `(session_id, tool_call_id)`) and return instantly — nothing double-executes, answered calls are skipped.

**What persists between iterations:** only `self.messages` plus `compaction_state`; the manager (`server/manager.py:persist_session`) flushes to disk at every parked prompt, so a crash mid-suspension loses nothing. Errors and interruptions persist as `role:"notice"` messages (kinds `error`/`interrupted`/`model_switch`/`compacted`) — reload-visible, provider-invisible; `retry()` is guarded on the history tail being an error notice (looking *through* model_switch notices, so switch-then-retry works).

**Pydantic AI mapping.** Most of this we have or have decided better: D47/D48 already make HITL pause a transcript checkpoint rather than a blocked worker — theirs holds an awaiting coroutine alive (and needs `_engines` cache + durable-resume machinery to survive restarts); ours is strictly stronger, keep ours. **Copy:** (1) the no-orphan invariant as an engine-level guarantee — on cancel/deny/interrupt, synthesize a `tool_result` item for every outstanding `tool_call` (we have the denial half via D48; the interrupt half needs stating); (2) steering (`queue_steering`) — injecting a mid-turn user message at the next loop checkpoint instead of colliding a second run, which our conversation lock (D61 territory) will want; (3) the retry-guard pattern (retry only when the tail is an error marker; a model switch must not consume the retry); (4) `_display` sidecars — tool-result metadata the *model must never see* but the UI needs (their example: how many results privacy filters hid — a count the model could probe around), which in our item store is a `meta` field the renderer strips. **Skip:** their thread+queue stream bridge (we're async-native, D29); ephemeral `<system-context>` appended to the last user message (we have `instructions` re-evaluated per run, D9, which is the same job done right).

## 2. Compaction, exactly (`coworker/compaction.py`, 561 lines — pure functions + one dataclass, engine owns when/with-what)

**Trigger:** `signal >= min(0.8 × context_window, 250_000)`, where signal = last provider-reported prompt-side `context_tokens`, falling back to chars/4 over serialized outbound messages. The 250k cap exists so 1M-context models compact early ("quality and latency degrade well before the nominal limit"). Checked between iterations, side-effect-free, so a COMPACTING event can precede the slow summarizer call.

**Boundary:** `pick_boundary` keeps a verbatim tail of `keep_tokens = 0.25 × trigger` (a token budget, not a turn count — "one huge tool loop shouldn't starve the working set"): earliest user-message index whose suffix fits; falls back to assistant-message (iteration) boundaries *inside* the newest turn when that turn alone blows the budget. A `tool` message may never head the outbound view.

**CompactionState** (persisted on the session record; the transcript is never mutated): `{boundary_index, summary_text, working_state, user_messages[], user_messages_dropped, created_at, model_used, trimmed}`. The outbound view = `[system?] + one user message containing the <compacted-history> block + verbatim tail from boundary_index` — and the block+tail are **byte-stable between turns, so prompt caching keeps working** (their stated design reason).

**Three components of the block, in trust order:**
- *LLM summary* — 8 mandated sections (primary request+standing constraints; decisions **with the why** — "a decision without its reason gets relitigated"; artifacts; errors+user corrections; all user messages; pending tasks; current work; next step), plus the rule "do NOT carry full file contents as truth — note THAT a file was read; stale memory of a file is worse than no memory", plus a continuation contract ("do not re-ask, do not recap, do not mention compaction").
- *Mechanical working state* — `extract_working_state()` walks the span's tool-call records, **no LLM**: files written (args `path`/`file_path` where tool name contains write/edit/append/save/create/patch, deduped recent-first, cap 20), last 10 `run_shell` commands with exit status parsed from the JSON result (`exit_code`/`error` keys), artifacts (url/path/title where name contains artifact/publish/deploy, cap 10), and the sorted tool-name set.
- *Verbatim user messages* — every user message in the span, chronological, whitespace-collapsed, clipped to 600 chars, capped to the newest **40 across repeated compactions** with an honest `user_messages_dropped` counter rendered as "(N earlier user messages omitted)". Rationale comment: "user words are the ground truth of intent and must not depend on an LLM remembering to include them."

**Summarizer call:** tools off, max 3k output tokens, span rendered compactly (tool results clipped to 400 chars — "huge and mostly stale; a file read 40 turns ago is better re-read"; whole render capped at 400k chars, oldest lines dropped). Re-compaction feeds the prior summary as head-of-span ("fold its still-relevant content in"), so summaries chain rather than nest.

**Failure policy:** one unconditional retry; then attended → Retry/Trim prompt via the question path; unattended → auto-trim ("never park a background run on internal bookkeeping"). `trim_state` advances the boundary past ~10% of remaining messages with no summary but the mechanical block and user-message list still built — deterministic state is free. **Overflow rescue:** a raw context-overflow 400 from the main model (`is_context_overflow` string-matches 8 provider phrasings) routes into `_compact_now(force=True)` instead of surfacing, progress-guarded (each pass must move the boundary forward or it gives up into the error path).

**Pydantic AI mapping.** Our renderer (`engine/renderer.py`) already has the superior skeleton: per-budget summary cache rows, conditional per-model views, seam-snapped cuts, truncation fallback + alert (D24/D25). What it lacks and should **copy**: (1) the deterministic mechanical-state block built from `tool_call`/`tool_result` items — for us this is a pure function over the summarized item range, appended to the summary cache row; zero hallucination risk, and it directly addresses the roadmap's "compaction before verification" KE signal; (2) verbatim user-message retention with the capped list + dropped-counter honesty; (3) the byte-stability property as an explicit test (summary block + tail identical across turns unless the boundary moved — protects provider prompt caching); (4) overflow-400 → forced re-render as a progress-guarded rescue path; (5) the 8-section summarizer prompt near-verbatim (it is the best summarization prompt I've seen shipped; ours is currently unwritten policy inside the injected `SummarizeFn`). **Change:** their chars/4 estimator is our `estimate_item_tokens` — keep ours; their trim fallback drops content irrecoverably from the *view* only (transcript intact) — same as ours, fine. **Skip:** the attended Retry/Trim prompt (our failure policy O6.7 already decided truncate+alert; a human prompt on an internal bookkeeping failure contradicts it).

## 3. Risk classes and permission layering (`coworker/risk.py` 58 lines, `coworker/permissions.py` 238 lines)

**Declaration is metadata, not schema:** every tool is registered with aisuite `ToolMetadata(category, risk_level, capabilities, requires_approval)` (see `tools/shell.py:559`), but the *risk class* is resolved by `risk.classify()`: user-local override (Phase-2 stub, always None) ?? by-name base table (`{write_file, replace_in_file, apply_patch, apply_unified_diff} → WRITE_LOCAL`, `run_shell → EXEC`) ?? `requires_approval → EXTERNAL` ?? `READ`. So EXTERNAL is the *default for anything that self-declares approval-worthy* — connector tools get it for free — and unannotated tools default to READ (a fail-open they accept because built-ins are vetted; we should not).

**Evaluation order in `PermissionEngine.evaluate`** (this ordering is the design): (1) read-only modes (DISCUSS/PLAN) deny anything consequential, `needs_user=False` — a hard wall the model can't prompt through; (2) **path scoping for writes runs in ALL modes, including AUTO** — a write naming a path outside a writable root is denied even at full access; (3) non-consequential → allow; (4) AUTO → allow; (5) session command allowlist (shell) — reject outright if the command contains any of `; & | > < ` $( ( \n \r` (one "allowlisted" command must not smuggle several), else `shlex.split` both sides and require the entry's tokens to be an exact token-prefix of the command's tokens (`git status` matches `git status -s`, never `git statusfoo`, never bare `git`; unbalanced quotes → not allowlisted); (6) session tool allowlist, **with connector tools excluded** (a session-wide "always allow send_message" is too broad); (7) task-scoped standing rules — see the orchestrator notes; deliberately NOT subject to the connector exclusion, because exact-target binding is what makes auto-allowing a connector tool safe, and never for EXEC ("shell asks forever"); (8) CUSTOM-mode config auto-allow; (9) `needs_user=True`. Roots are held **by reference and re-read every check**, so a mid-session folder grant applies without rebuilding the engine.

**Shell hardening beyond the gate** (`tools/shell.py`): one persistent bash/PowerShell process behind an `Executor` ABC (their stated hedge for a future ContainerExecutor — our D38 sandbox port is the same seam, already decided); marker-line protocol `<uuid-marker> $? $PWD` for exit code + cwd tracking; timeout ladder (default 120s, model-requestable up to 600s; first deadline SIGINTs the foreground child and keeps reading until the marker resyncs the stream, 3s grace, then hard-kill + respawn in last cwd — self-healing, session continues); non-interactive env (`GIT_TERMINAL_PROMPT=0`, `DEBIAN_FRONTEND=noninteractive`, `PIP_NO_INPUT=1`); output truncation keeps the **tail** ("builds and test runners put the verdict at the end"); background tasks are separate detached process groups with incremental-read cursors (`shell_task_output` returns only new-since-last-read), deliberately not killed by shell recovery. The `run_shell` schema takes a `description` argument used *only* by approval prompts and audit ("intent, not just the raw command").

**Pydantic AI mapping.** **Copy:** (1) the four-class taxonomy as a field on our tool-registration record (D33's `register_tool`) — `read | write_local | exec | external` — with `external` as the class that drives approval routing; it is orthogonal to and composes with D46's `requires_approval`/`approval_predicate` (theirs conflates the two by deriving external *from* requires_approval; keep them separate and make **unannotated = external, not read** — fail-closed where they fail open); (2) the shell-operator disqualifier + token-prefix allowlist matcher verbatim if/when we grow a command allowlist for the sandbox; (3) path-scoping that applies even in full-access mode; (4) tail-keeping truncation and the `description` argument on any exec tool. **Change:** their modes (DISCUSS/PLAN/INTERACTIVE/AUTO/CUSTOM) are a per-session enum; ours should be per-agent-spec data (D21 capabilities style) with the read-only wall expressed as "no tool whose class > read is even in the tool table" where possible — filtering beats gating. **Skip:** the persistent-shell REPL protocol (our sandbox is containerized exec, D38/D53; the marker dance is a workaround for not having one).

## 4. Audit write path (`coworker/audit.py`, 174 lines)

Single append-only SQLite table, written synchronously under an RLock from an `audit_sink` callable injected into the engine; engine-side `_audit()` swallows sink exceptions (audit failure never breaks a turn — note: that also means audit is best-effort, not a guarantee). Schema: `audit_events(id, timestamp DEFAULT CURRENT_TIMESTAMP, session_id, agent, workspace, connector, tool, stage, status, approval, args, result_preview, reason, resource)`. `stage` is the interesting column — observed values: `proposed`, `auto_allowed`, `approval_requested`, `approval_resolved`, `started`, `filtered`, `finished`, `plan_proposed`, `directory_requested`, `question_requested`, `standing_rule_minted`. One tool call therefore leaves 2–4 rows telling the whole authorization story; `approval` records the outcome vocabulary (`once`/`always_tool`/`deny`/…), and every auto-allowed call **cites its rule in `reason`** ("allowed by standing rule: send_message → slack:C0123") — their §25 invariant.

**Redaction is at write time, key-name-based** (`_sanitize_args`): any arg key containing `token|secret|password|api_key|access_token|bot_token|app_token|raw` → `"[redacted]"`; `browser_type`'s `text` arg → `"[redacted input]"` (keystrokes could be a password); keys equal to or suffixed `_body|_content|_html` → `"[redacted body]"` (message bodies are PII, the audit only needs that a send happened); everything else `_summarize`d (strings truncated to 500 chars, lists capped 10, dicts capped 20 keys). `_resource()` extracts one queryable identifier from args by priority (`url, owner, repo, issue_key, page_id, ticket_id, calendar_id, message_id`, plus `subdomain→*.zendesk.com`, falling back to `result.url`). `result_preview` is 300 chars, newline-escaped.

**Pydantic AI mapping.** **Copy:** the `stage` column concept — our transcript items (D24) already capture proposed/result, but the *authorization* stages (approval_requested/resolved with outcome, auto_allowed with cited rule, standing_rule_minted) are exactly what D47/D48's pause/resume should emit as audit-kind items or a parallel table; and the every-auto-allow-cites-its-rule invariant. **Copy with upgrade:** key-name redaction is necessary but not sufficient for us (a secret pasted into a `command` string passes their filter) — combine their key-based pass with a value-based scan over known secret formats before any item leaves the process boundary; their `raw` key in the secret list is a nice catch (aisuite convention for raw payloads). **Skip:** SQLite specifics; swallowed sink errors — ours should at minimum count failures (Sentry, D8).

## 5. Selfwake store (`coworker/selfwake.py`, 185 lines) — **read this section with its defect**

Record: `Wake{id: uuid4hex, session_id, kind: timer|completion|event, state: pending|due|fired, fire_at: ISO?, job_id?, event_key?, note, created_at}` in a JSON file (`wakes.json`) behind a lock. Agent-facing tools (knowledge personas only): `sleep_for(seconds)`, `sleep_until(iso)`, `wake_on(job_id)` (a `run_shell` background task id), `wake_on_event(event_key)` — the agent calls one and *ends its turn*; there is no held coroutine, which is why idle cost is ~zero. Scheduler tick (30s, `automation/scheduler.py`) calls `manager.resume_due_wakes()` as `extra_tick`: for each `due()` wake, deliver a wake message to the session via the shared busy→steer / idle→background-turn path, then `mark_fired` **in a `finally`, even when resume raised** — a wake fires at most once; a failed resume is lost (no retry, no dead wake state).

`due()` semantics: timer wakes fire on `fire_at <= now`; completion/event wakes fire only when previously flipped `pending→due` by `complete_job(job_id)` / `fire_event(event_key)`. **Defect found by grep, worth recording because the first-pass review and our blueprint adoption item assume otherwise: at this commit nothing in production code ever calls `complete_job` or `fire_event`** — the only callers are `tests/test_self_wake.py`. Nothing watches background-task exit (`_BackgroundTask` has no completion callback; the scheduler never polls `proc.poll()` against armed wakes), and `KIND_EVENT` is marked Phase 3. So an agent that calls `wake_on(job_id)` at this commit **sleeps forever**; only timer wakes actually work end-to-end. The *shape* (arm → suspend → external completion flips due → tick drains) is still the right one; the shipped artifact just hasn't closed the loop.

**Pydantic AI mapping.** Our D35 detached background work + the dsh reference's job seam are the neighbors here. **Copy the shape, not the code:** a wake table `(id, conversation_id, kind, fire_at | job_id | event_key, state, note)` with pending→due→fired and at-most-once firing, drained by whatever tick we already run — and the resume being "append a wake user-turn to the conversation and run it" (their wake messages are good copy: "⏰ Wake — the job `X` you were waiting on has completed. Continue where you left off."). **Change:** (1) actually wire completion — for us the natural closer is the background-task's own completion callback (we control the sandbox port) flipping the wake, not a poll; (2) a failed resume should retry or park visibly (their fire-in-finally silently eats it — their own `unrouted.py` dead-letter store exists for exactly this and isn't used here); (3) wakes JSON-file storage → our Postgres. This also generalizes: D47's paused runs and wakes are the same "suspended conversation + external resume trigger" record; consider one table with `trigger_kind ∈ {approval, timer, job, event}`.
